# Deploying TGL to Render + Supabase

One Render web service (Docker) serves everything from a single origin:

```
Browser ──► https://<your-domain>  (Render web service, Dockerfile)
              ├── /               public site (prerendered) + member app (/login, /app/…)
              ├── /admin          admin dashboard
              └── /api/…          FastAPI
                     ├──► Supabase Postgres   (all records)
                     ├──► Supabase Storage    (payment proofs, PRIVATE bucket)
                     └──► Resend              (signup / login / reset emails)
```

Same origin is deliberate: the session cookies are `HttpOnly; Secure;
SameSite=Strict`, which only works when the site and API share an origin.
Accounts and sessions are the app's own (Argon2 + signed cookies) — Supabase
Auth is not used, so there is no Supabase key in the browser at all.

## 1. Supabase (≈5 minutes)

1. Create a project at <https://supabase.com/dashboard> (region: **Mumbai
   `ap-south-1`** is closest to Bengaluru). Save the database password in a
   password manager.
2. **Database URL** — *Project Settings → Database → Connection string →
   **Session pooler***. Copy it and put your password in it. It looks like
   `postgresql://postgres.<ref>:<password>@aws-0-ap-south-1.pooler.supabase.com:5432/postgres`.
   Use the session pooler: it is IPv4-reachable from Render (the direct
   connection is IPv6-only on new projects).
   Paste it exactly as shown — a password containing `@`, `!` or `:` does
   not need manual percent-encoding; the app handles it. The connection is
   TLS-encrypted (`sslmode=require`, Supabase's default). For full
   certificate verification, download Supabase's CA (*Database → SSL
   Configuration*), add it to the image and set `DATABASE_SSL_ROOT_CERT`.
3. **API** — *Project Settings → API*: copy the **Project URL**
   (`https://<ref>.supabase.co`) and the **service_role / secret** key.
   The service key bypasses all access rules: it goes only into Render's
   environment, never into code, chat, or the frontend.

> **The production Supabase project is already provisioned** — tables,
> RLS lockdown and the private bucket were created and verified on
> 2026-10-05. Re-running is harmless.

Nothing else to click. On first boot the app:

* creates its tables (and adds any missing columns on later deploys),
* **enables Row Level Security on every table with no policies and revokes
  the `anon` / `authenticated` grants** — so Supabase's auto-generated Data
  API exposes nothing even to someone holding the public anon key; the app
  itself connects as the table owner and is unaffected,
* creates the private `payment-proofs` Storage bucket (2 MB limit, images +
  PDF only).

## 2. Resend (email)

Signup, OTP login and password reset codes are emailed via
[Resend](https://resend.com). Verify the sending domain (`skykeen.in`, DNS
records per `docs/P0_IMPLEMENTATION.md`) and create an API key. Without it
the site works but **nobody can verify an account** — the server logs
`RESEND_API_KEY is not set` at boot.

## 3. Render

1. Push this repo to GitHub (see §5).
2. Render dashboard → **New → Blueprint** → select the repo. Render reads
   `render.yaml` and asks for each secret:

   | Variable | Value |
   |---|---|
   | `DATABASE_URL` | Supabase session-pooler URL from §1.2 |
   | `SUPABASE_URL` | `https://<ref>.supabase.co` |
   | `SUPABASE_SERVICE_ROLE_KEY` | service_role / secret key |
   | `PUBLIC_ORIGIN` | the public URL, e.g. `https://tgl.skykeen.in` (or the `onrender.com` URL until the domain is attached) |
   | `RESEND_API_KEY` | from §2 |

   `SECRET_KEY` is generated by Render. Everything else has a value in
   `render.yaml`.
3. Deploy. The health check is `GET /api/health`.
4. **Create the admin login** (Render → the service → *Shell*):
   ```
   python create_admin.py
   ```
5. **Custom domain** — Render → *Settings → Custom Domains* → add
   `tgl.skykeen.in`, then create the CNAME it shows at your DNS provider.
   Update `PUBLIC_ORIGIN` to match. (The site's canonical/OG URLs already
   point at `https://tgl.skykeen.in`.)

## 4. Verify the live deployment

Run the checks in `scripts/smoke-live.sh <URL>` (no data written), then by
hand on a phone and a laptop:

* `/` renders; `/login`, `/signup`, `/app/networking` deep links load;
  a made-up path shows the TGL 404 page.
* Sign up with a real inbox → code arrives → onboarding → `/app/vertex`.
* Submit one registration with a real screenshot → it appears in `/admin`
  and the screenshot opens there. Then delete that test entry in `/admin`
  (this also deletes the stored file).

## 5. GitHub

```
git push -u origin production-readiness
```
then open a PR into `main` (or point the Render Blueprint at this branch).
`.env` files, `backend/var/` (local database and uploads) and build output
are git-ignored; only `*.example` files with empty values are committed.

## Operations notes

* **One instance.** Rate limits are in-process (`app/ratelimit.py`); keep the
  service at 1 instance unless they are moved to Redis.
* **Proxy hops.** `TRUSTED_PROXY_HOPS=1` makes rate limits key on the IP
  Render's load balancer saw. After the first deploy, confirm the logs show
  real client IPs rather than one shared address; adjust if Render's edge
  adds another hop.
* **Backups.** Supabase takes daily backups on paid plans; on the free plan,
  schedule `pg_dump` yourself. Proofs live in the Storage bucket.
* **Free plans.** Render free sleeps after 15 idle minutes (~1 min cold
  start); Supabase free pauses after a week of inactivity. Fine for staging,
  not for registrations.
